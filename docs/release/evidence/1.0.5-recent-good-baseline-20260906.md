## 同一基线上的间歇性分叉（2026-09-06）

回退并运行同一 SHA 后，`listener-type.log` 记录到两种完全不同的路径，这正是“有时好、有时坏”的可重复证据，而不是一次主观印象：

- session `800`–`812`：连续候选均为 `kws_hit=false`，stage-2 为 `Absent`，主人分数约 `0.02–0.15`，最终在 `2.72–4.28 s` 被 `enrolled_non_match` 拒绝；这是“没有唤醒”的候选拒绝/清理，不是硬件重启。
- session `813`、`814`：约 `1.8 s` 的 stage-2 才得到 `ExactStart`，随后 owner match 并接受。对应 capsule 首次非空预览约 `1197/1217 ms`，但日志中的 `wake_to_capsule_request_ms=1667/1654`，仍超过 1500 ms ceiling。

这组日志把剩余根因缩小到唤醒前端：stage-1 KWS 经常没有命中，系统只能等 1.8 s 的 stage-2 全窗口确认；stage-2 一旦命中，后面的 owner/preview/stop 链路可以工作。当前不能把它归因成“声纹模型坏了”，也不能把 `actor_restart`（拒绝候选后的后台 listener 重置）误判为固件自发重启。下一步应在不改结束阈值的前提下，沿 KWS 输入窗口、音频幅度/归一化和 detector 调度记录证据。

## 观测动作与真实复位的区分

2026-09-06 的一次只读串口抓取保存于 Firmware `tests/artifacts/serial现场_20260906-latest-50s.log`。其第一行硬件启动原因明确为 `rst:0x15 (USB_UART_CHIP_RESET)`，不是 `interrupt_wdt`；之后的 50 秒串口没有新的 WDT/异常，且出现了 `boot_safety: normal boot survived 30000ms`。Type 同一时间段记录到 BLE `Disconnected`，随后自动恢复。因此“抓日志后突然变差”的这一次，是 COM5/USB Serial-JTAG 打开造成的 USB 复位及 BLE 重连延迟，不能作为模型或录音状态机回归证据。

`diag_log_20260906-123022.jsonl`、`123944`、`172139`、`172806`、`183820`、`193408` 中的 `interrupt_wdt(5)` 记录来自 RTC 保留环（时间序列为约 32.6 s → 重新启动 → 约 32.6 s），它们证明过去确实发生过 WDT，但这些按不同时间导出的文件内容完全相同，不能证明导出当下又发生了新的 WDT。以后必须同时保存串口启动行和导出前后的 uptime，才能把“历史保留事件”“串口诱发 USB reset”“产品运行中自发 WDT”分开。

## 这条基线实际包含的修复

`3aa3b31` 之前的代码已经合入以下几类收敛措施：

1. `9e04f3e` 统一唤醒候选仲裁入口；
2. `d2c836d` 集中候选传输停止，避免多个回调各自发送 STOP；
3. `84ccf52` 对主人尾音做有界保护，避免句中截断；
4. `c072958` 隔离 BLE orphan session，避免恢复风暴污染新会话；
5. `3aa3b31` 将新鲜 USB reset 证据单独归类，避免把串口读取造成的复位误判为自发 WDT。

因此“好”不是某一个模型阈值的偶然结果，而是候选、停止、主人端点和 BLE 恢复在同一条已观察过的路径上没有互相抢状态。

## 后续为什么会被改坏

回退前的后续提交不是单点修复，而是在同一时间改动唤醒候选、预览可见性、主人 body presence、端点计时和终止清理。`3aa3b31..1f394ab` 共涉及 16 个文件，约 `1064` 行新增、`287` 行删除；没有按单一不变量逐提交做真实链路门禁。这造成了“修一个症状、改变另一条状态边界”的回归面：

- `a19cee2` 把胶囊从“本地完整短语确认后显示”提前到“stage-1 KWS 命中即显示”。候选 UI token、拒绝 dismiss、真实 owner session 三者开始跨回调配合，增加了候选与真实会话交接竞态。
- `5e24633`、`d6592c3` 又把本地候选提前显示和跨物理窗口延迟激活叠加到这条交接链路上；唤醒反馈更早，但 owner 激活可能跨窗口/跨代际等待，容易表现为慢或无反应。
- `398a221` 改写不确定主人尾音的 wall-clock 释放条件。它能避免永久 hold，但也改变了自动结束的时间边界；这类改动必须和“句中不能截断”一起做时序验收，不能只看单元测试。
- `fe35a81` 一次性重写 provider 回调、preview reducer、body presence 和最终文本入口（9 个文件，约 452 行变更），把“显示中的 provisional”与“权威主人正文”放进了新的联动路径。其后 `caddf08`、`1f394ab` 又改变终止清理和严格前缀收敛规则，导致合法 ASR 修订可能不再可见，或在终止边界没有可提交文本。

回退前日志中有直接反例：session `019cb014-b003-4188-addc-8e5e1ebb4978` 在 0、1033、2092 ms 都是空预览，3030 ms 进入 transcribing，5352 ms 直接回 idle，期间没有非空 preview 或 insertedChars。这与上述“大量状态同时变化、但没有单一可验证 owner/preview/stop 事务”的结构性回归一致。

这里的结论是结构性结论，不是把责任归因给声纹模型：模型输出只是输入，回归发生在多个输入对同一个生命周期的竞态和门禁顺序上。单元测试通过并不能证明真实 BLE → ASR → capsule → stop 闭环仍然成立。

## 后续修改规则

所有修复从本记录对应的 `v1.0.5-good-20260906` 开始，遵守以下门禁：

1. 候选显示、owner 激活、预览提交、自动结束、STOP、关闭各自只能由统一生命周期 reducer 提交；
2. 一次提交只改变一个状态不变量，并保留其余基线行为；
3. 每次改动必须跑 `target_speaker_endpoint` 与 `pending_` 测试，并用最新 release 运行时校验；
4. 没有 capsule 时间线和真实 BLE 闭环证据，不得把“更灵敏”或“更快”称为修复；
5. 干扰、重启、吞字、提前结束、结束过慢分别记录证据，禁止用全局阈值掩盖 hold reason。

## 验收解析器边界修正（2026-09-07）

旧版 `scripts/check-live-wake-endpoint.mjs` 把产品日志里的
`wake_to_capsule_request_ms`（候选开始到胶囊请求）当成“接受唤醒到 Recording”，
并把 provider 首包事件当成胶囊首字预览。这两个时间轴不是验收合同的边界，会把
正常的候选确认耗时和网络首包延迟误报成状态机失败。

现在脚本以同一 session 的真实事件计算：

- `automatic streaming gate ... gate_decision=Accept` → 首个可见 `state=Recording`；
- `automatic body started after capsule` → 首个可见 `has_message=true message_chars>0`；
- provider 首包保留为诊断字段 `providerPreviewLatencyMs`，不替代胶囊首字。

脚本 schema 已升为 `2`，旧的候选起点耗时保留为
`candidateToCapsuleMs`；`wakeToCapsule*` 仅作为兼容别名，值改为接受唤醒边界。
用当前日志的 3 个有主人证据会话运行 `--required-samples 3` 得到：

```text
status=PASS
acceptedToRecordingP95=2 ms
firstNonemptyPreviewP95=0 ms
settledTargetToEndpointP95=947 ms
stopToDoneP95=458 ms
providerPreviewMax=7495 ms (diagnostic only)
```

这次修正只修验收边界，没有修改 Type/Firmware 的产品状态机或阈值；后续机器闭环必须
继续使用该事件边界，不能再用候选总时长或 provider 网络首包代替产品体验指标。

`check-live-wake-only.mjs` 同步使用“accepted wake → 前台 Recording”作为
`wakeToVisible` 的合同指标，候选开始→前台显示另存为 `candidateWakeToVisible`。
因此两个验收工具不会再因为候选确认耗时不同而给出互相矛盾的唤醒结论。

本文件冻结的是“可用起点”，不是根治完成声明。后续若再次回退，必须保留新旧二进制 SHA、提交范围和对应 session 时间线，不能只写“体验变差”。
