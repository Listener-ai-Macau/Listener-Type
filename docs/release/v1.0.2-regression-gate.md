# Listener Type v1.0.2 Regression Gate

This gate exists because v1.0.2 touches Bluetooth recovery, BLE name refresh, OTA, recording BLE, and LED coordination at the same time. A v1.0.2 package is releasable only after the automated runner passes and the manual hardware observations below are recorded.

## Automated Gate

Run from the Listener-Type repo:

```powershell
pwsh -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-v1.0.2-regression.ps1 -SkipPackage -SkipHardware -SkipNpmCi
pwsh -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-v1.0.2-regression.ps1 -OnlyHardwareProbe -SkipNpmCi
```

The hardware probe is intentionally isolated. Frontend/Rust checks can write
BLE-flavored runtime logs and exercise mock GATT paths, so the real tray-owned
BLE notify probe must run as its own short step before any final full gate.

Use `-SkipPackage` only while iterating locally. A release candidate must also
run the package step without `-SkipPackage` before publishing.

The runner records logs under `.artifacts\v1.0.2-regression\`.

## No-Regression Matrix

| Area | Must Not Regress | Evidence |
|---|---|---|
| Startup and tray | Latest release exe opens the real UI, not a blank WebView; tray can be opened after restart. | `cargo build --release --target x86_64-pc-windows-msvc`, package smoke, manual tray launch. |
| BLE link to Type | Windows may show the device connected while WinRT paired services refresh; Type must still recover via exact advertised address/BTHPORT cache and reach the embedded audio BLE service. | `listener-type.exe --probe-embedded-audio-ble-subscription 12000`; `--read-embedded-audio-ble-status 12000` reports `connected=true`. |
| Pairing cache cleanup | Background cleanup must not repeatedly call Windows PairAsync, repeatedly open Bluetooth Settings, or spam failed Windows connect toasts. | Type logs show cleanup/handoff only; no repeated prompt loop during idle. |
| Manual Windows removal / computer switch | If a user deletes Listener from Windows or double-clicks to move to another computer, Type must not automatically pair the old PC back from a matched-but-unpaired stale Windows node. Auto rebuild is allowed only after Type-controlled recovery or when Windows still proves the device is paired. | Backend tests for manual-unpair hold; Type logs show no background PairAsync after manual removal. |
| BLE name | Default is `listener`; any 1-29 visible ASCII name is accepted; same-name write must not reset pairing; changed name must write firmware name and reconnect Type without automatic unpair, PairAsync, or Windows pairing prompt. Explicit re-pair remains the double-click/native Windows pairing flow. | `cargo test device_ble_name --lib`; manual same-name and random-name check. |
| Recording BLE | The recording path keeps Type-ready alive during processing and sends `TYPE:BYE` only on real teardown. | `npm run check:embedded-ble-processing-led`; firmware recording BLE matrix/manual recording smoke. |
| OTA | Type loads v1.0.2 OTA packages, rejects downgrade/lower package warnings correctly, and can discover OTA v2 GATT when the device is paired. | `cargo test firmware_ota --lib`; firmware OTA package/probe; manual OTA attempt when required. |
| Double-click repair | Explicit recovery is a user action: it clears stale pairing, opens one recovery window, and then uses Windows native pairing/manual Settings handoff. It must not create connect/disconnect churn. | Firmware repair gate plus Type log review. |
| Release package | Denzic root receives only the current MSI for Type; no portable zip is shipped for Type. | `scripts\windows-package-msvc.ps1` default package output; root cleanup check. |

## Manual Hardware Acceptance

Record one observation per action. Do not batch these into a long prompt. The
final preproduction physical gate is the single scripted entry point below:

```powershell
pwsh -NoProfile -ExecutionPolicy Bypass -File .\scripts\windows-listener-preproduction-human-review.ps1
```

Use `-ListSteps` to preview the exact acceptance sequence without opening any
human prompt. The generated summary must be `HUMAN_REVIEW_PASS` before packages
can be copied to the Denzic root or published as v1.0.2.

1. Same-name write: set BLE name to the current firmware name. Expected: no re-pair, no Windows pairing toast, Type remains connected.
2. Random-name write: set BLE name to a new random visible ASCII name, for example `listenerR7`. Expected: firmware advertises exactly that name, Windows cache is refreshed, and Type reconnects after native pairing.
3. Double-click repair: double-click the knob once. Expected: firmware shows the three-cycle blue double-flash repair cue, opens a recovery pairing window, and does not treat a single click as double-click.
4. Recording smoke: start a normal recording from the intended trigger. Expected: capsule appears quickly, BLE audio transfers, processing LED does not interrupt recording/key/knob LEDs, and final text/history is produced or a clear failure is logged.
5. OTA smoke: run one OTA preflight/probe before transfer. Expected: OTA service and characteristics are discoverable and firmware OTA LED state is visible during transfer/preflight.
6. Tray launch: start the latest packaged exe from tray/shortcut. Expected: UI is not blank and logs show the frontend loaded.

## Release Rule

If any row fails, do not bump/copy packages. Fix the failing row, rerun the affected automated command, then rerun this gate before publishing v1.0.2.
