# Listener Type 1.0.6 RC1 — build 20

Windows x64 release candidate, refreshed on **16 October 2026**.
The existing `v1.0.6-rc1` release supplies build 20. It remains a **prerelease**;
the stable automatic-update channel is unchanged.

## Install and matching firmware

- Install `ListenerType_1.0.6-rc1_x64_en-US.msi` and verify `SHA256SUMS.txt`.
  The MSI is 297 MB (283 MiB), supports same-version RC1 upgrades and retains settings and voiceprints.
- Matching [Listener Firmware RC1](https://github.com/Listener-ai-Macau/Listener-Firmware/releases/tag/v1.0.6-rc1):
  **`9d92421e915196b4`**, Listener keyboard-v2 / ESP32-S3 N16R8. Firmware image unchanged.
- Only the Windows MSI and checksum file are supplied. The executable and installer are unsigned.
- Recognition requires the user's supported provider credentials. A hosted subscription service is not included.
- The optional Chinese content-recovery model downloads to the per-user cache when enabled (about 890 MB).
  Ordinary cloud recognition does not wait for this optional download. Bundled license notices are retained.

## Changes since public build 13

- Build 14: bounded personal-activity PCM backlog by source bytes, recovered after gaps/overruns,
  and prevented retired workers from publishing evidence into a newer generation.
- Build 15: advanced natural-reference acquisition past a rejected early candidate without lowering quality gates.
- Builds 16 and 18: bound wake identity to the actual keyword source and provided the existing 1.1-second,
  same-capture identity context for a valid shorter keyword. Build 18 corrects the too-short-input regression in build 16.
- Build 17: prevented old absence observations from ending a recording before a new speech onset is analyzed.
- Build 18: physical-button takeover uses the same request-tagged capture continuation as voice wake;
  an unconfirmed predecessor STOP cannot finalize the new recording.
- Build 19: maintained the visible capsule's topmost layer through native Windows events without taking focus,
  moving it or showing a hidden capsule.
- Build 20: kept one outstanding identity job per wake candidate. Partial hits cannot enqueue replacement work
  on every audio append; live and terminal admission share exact-source verification.
- Build 20: when capture continuation fails after the owned source really stopped, preserve its collector
  and perform normal audio drain, final text, history and clipboard closeout. Retired continuation receipts
  cannot create another recording. A deadline alone does not terminate active speech.

Builds 11–13 remain included: complete history text is the clipboard recovery source, capsule events retain
recording ownership, and queued device processing-light hints retain their session and revision.
Earlier streaming, input-receipt, early-checkmark closeout and on-demand asset fixes remain included.
No new model, identity threshold, paid service or stricter body-text filter is introduced.
Unlinked research candidates, private recordings, credentials and personal voiceprints are excluded.

## Evidence and remaining issues

The existing saved failure audio, targeted state regressions and native capsule/window checks support these changes.
The installed build 20 executable matches the packaged payload. In the saved slow-wake case, the production
verification lane performed 2 comparisons instead of 45 tasks/44 replacements. Warm replay waited 159 ms,
versus the original live log's 6593 ms, with the same identity score. This is not a new live latency guarantee
or a controlled comparison under identical system load. Cold-process initialization still took 8951 ms.
The original 6-second capture also passed the affected physical-EOF/continuation state path.
These results do not establish full new hardware/editor acceptance or eliminate every daily-use defect.

Known remaining issues:
- First-process initialization can still be slow. An earlier unexplained application exit remains unresolved.
- Strong external speech may require repeated wake commands, false wakes or foreign text may occur,
  and continuous background speech can still affect automatic closing. Reliable speaker isolation is not claimed.
- A 16 October Bluetooth rename updated and read back the name, but Windows pairing repeatedly failed
  and the UI took about 129 seconds to finish. Reconnection was not confirmed by that name readback.
  This existing rename/pairing path remains under investigation; it is not fixed by build 20.
- Global language support depends on the configured recognition provider; arbitrary overlap acceptance is incomplete.
